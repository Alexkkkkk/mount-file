CI-матрица держит 3.10 как рабочий пол: `ci.yml:43` — `ubuntu-latest` × 3.10/3.11/3.12; `ci.yml:45` — полная матрица `windows-latest` × 3.10/3.11/3.12 и `macos-latest` × 3.10/3.12; `ci-nightly.yml:25` и `release.yml:98` — тоже `3.10`. Базовый образ Docker — `python:3.15-slim` (`Dockerfile:4`).

### 12.2 Совместимость (проверено)

| Версия Pillow | `Requires-Python` | Загружена |
|---|---|---|
| 13.0.0 (latest на PyPI) | `>=3.11` | 2026-10-16 |
| 12.3.0 | `>=3.10` | 2026-07-01 |
| 12.2.0 / 12.1.1 / 12.1.0 / 12.0.0 | `>=3.10` | — |
| 11.3.0 | `>=3.9` | — |

Release notes 13.0.0, раздел «Backwards incompatible changes», подраздел «Python 3.10»: «Pillow has dropped support for Python 3.10, which reached end-of-life in October 2026.» — [pillow.readthedocs.io](https://pillow.readthedocs.io/en/stable/releasenotes/13.0.0.html). Итог: **13.0.0 несовместим с 3.10; последняя совместимая ветка — 12.3.0.**

### 12.3 Вывод

1. **Разрешение уже корректное.** `uv.lock:1528-1529` уже содержит ровно ту пару, которую предлагалось «добавить»: `12.3.0` для `<3.11`, `13.0.0` для `>=3.11`. Установка через lock на 3.10 не ломается; `pip` тоже уважает `Requires-Python`, поэтому `Pillow>=10.0` на 3.10 разрешится в 12.3.0. Утверждение «Pillow 13.0.0 создаёт проблему для заявленной поддержки 3.10» в части **установки** не воспроизводится.
2. **Реальное расхождение — декларация.** Один пакет объявлен тремя разными нижними границами: `>=10.0` (`pyproject.toml:82`), `>=12.3.0` (`requirements-all.txt:8`), сплит по версии Python (`uv.lock:1528-1529`). `pyproject.toml` — единственный манифест, который читает внешний пользователь, и он не отражает фактическое требование: на 3.10 нужен `12.3.0`, а не «что-нибудь от 10.0».
3. **Главный риск не в версии, а в безопасности.** На 3.10 остаётся 12.3.0, а патченного 12.x нет — поэтому `security.yml:38-43` уже разрешает список из ~30 GHSAs, включая четыре critical Pillow-адвизори. Это зафиксировано в комментарии workflow, но не в README и не в трекере: пользователь Python 3.10 получает заведомо уязвимый Pillow без предупреждения.
4. **Pillow не в runtime.** `grep -rn "from PIL\|import PIL"` по `mountfile/` и `main.py` — пусто: пакет живёт только в опциональном extra `images`. Значит ужесточение пина не затрагивает базовую установку.

### 12.4 Предлагаемое действие

- `pyproject.toml:82` — заменить на маркерную пару, совпадающую с lock:
  `images = ["Pillow>=12.3.0,<13; python_version < '3.11'", "Pillow>=13.0.0; python_version >= '3.11'"]`
- `requirements-all.txt:8` — оставить `>=12.3.0` (совпадает с полом 3.10) либо убрать дубль, оставив extra `images`.
- В README рядом со строкой о Python 3.10 — явно сказать, что на 3.10 extra `images` тянет 12.3.0 с известными адвизори, а не «поддерживается полностью».
- Пересмотреть `allow-ghsas` в `security.yml` при выходе патча 12.x; до этого — не ставить extra `images` в CI-леги 3.10 без необходимости.
- Альтернатива, если 3.10 не нужен: поднять `requires-python` до `>=3.11` — Pillow сам объявил EOL 3.10 в октябре 2026, и это снимает весь класс проблемы.

### 12.5 Не подтверждено

- `uv.lock:1766` — в блоке резолюции 13.0.0 видна строка `"python_full_version >= '3.14'"`, тогда как зависимость на `:1529` помечена `>= '3.11'`. Возможно, список `resolution-markers` содержит несколько значений и видна только первая строка — **требует отдельной проверки**, противоречием не считаю.
- Утверждение про CVE/TOCTOU и версию исправления `filelock` к Pillow не относится и здесь не проверялось.
- Совместимость Pillow 13.0.0 с Python 3.15 (базовый образ Docker) отдельно не проверялась; в release notes упомянута официальная поддержка 3.15, дословную строку не цитирую.

## 13. Оракул для NTFS

Сверка на `main` @ `d4e29f7` (v1.100.1), 2026-11-21. Оракул здесь — эталон ожидаемого поведения, с которым сравнивается replay. Всё ниже либо прочитано в дереве, либо подтверждено документацией; непроверенное помечено явно.

### 13.1. Что уже есть в дереве

| Компонент | Файл | Роль | Авторитетность по собственному коду |
|---|---|---|---|
| `probe_ntfs_log` | production gate | предварительная проверка `$LogFile` | **не оракул**: «the production gate (`probe_ntfs_log`) alone is not an oracle, it shares code with the replay it validates» — `tests/test_ntfs_acceptance_independent_checker.py` (docstring) |
| `ntfsfix -n` | `tests/_independent_checkers.py`, `mountfile/journal_safety.py:109`, `mountfile/ntfs_native_writer.py:7` | грубая проверка «том не развален» | вторичное: «A successful `ntfsfix` invocation is intentionally inconclusive: ntfsfix is not a full NTFS consistency checker or a replacement for chkdsk»; `journal_safety.py` — «never treats ntfsfix as authoritative»; в матрице `checker_authoritative: false` |
| синтетические crash-фикстуры | `tests/ntfs_crash_fixture.py` | 5 сценариев (#530 P1) | provenance ограничен: «it is not a byte-for-byte Windows capture» |
| Windows-харнесс | `scripts/windows_ntfs_acceptance.ps1` | VHDX + реальный `chkdsk` | `checker_authority = "windows_native"`, но сам себя ограничивает: «does not prove NTFS replay parity or Windows crash-fixture equivalence» |
| компаратор replay ↔ chkdsk | `scripts/compare_ntfs_replay.py` | 4 потока байт-в-байт, типизированные исходы | доказывает **parity replay**, а не авторитетность чекера |
| байтовый диф | `scripts/compare_ntfs_snapshots.py::compare_file` | sha256 + число различающихся байт + первый offset | инструмент, не оракул |
| матрица чекеров | `docs/generated/checker-matrix.json` | инвентарь | единственная NTFS-строка: `ntfs-native-ro | ntfsfix | checker_authoritative: false | availability: unavailable | parity: not_claimed` |

**Ключевой дефект матрицы.** У ext2, FAT12/16, FAT32, exFAT есть авторитетная строка (`e2fsck`, `fsck.fat`, `fsck.exfat` — все `checker_authoritative: true`). У NTFS авторитетной строки **нет вообще**: присутствует только read-only профиль с `ntfsfix` и `checker_authoritative: false`. То есть проблема C6 — не «слабый оракул», а отсутствие оракула в модели. Сам `scripts/checker_matrix.py:4-5` это признаёт: «The report is intentionally a capability/availability inventory, not a parity verdict.»

### 13.2. Лестница авторитетности O0–O5

| ID | Источник | Что доказывает | Чего не доказывает | В дереве |
|---|---|---|---|---|
| **O0** | `probe_ntfs_log` | внутренняя согласованность модели | ничего внешнего — общий код с replay | есть |
| **O1** | `ntfsfix -n` | том не развален грубо; dirty-флаг | не chkdsk; «NOT a Linux version of chkdsk» (man page) | есть, вторичный |
| **O2** | монтирование `ntfs3` (ядро Linux), read-only на копии | **независимый** парсер ядра читает `$MFT`/`$INDEX`/имена и отдаёт их через VFS | не Windows-семантику целиком; сам драйвер умеет replay | **нет** в acceptance (runtime монтирует `ntfs-3g`, не `ntfs3`) |
| **O3** | `chkdsk /f` + `chkdsk /scan` на Windows-раннере | восстановление эталонным чекером Windows | не parity: chkdsk делает свой, более тяжёлый ремонт | harness есть (`windows_ntfs_acceptance.ps1`), строки в матрице нет |
| **O4** | `compare_ntfs_replay.py` | побайтовое совпадение `$MFT`/`$MFTMirr`/`$BITMAP`/`$LogFile` | зависит от O3: без него сравнивать не с чем | есть |
| **O5** | Windows-захваченный crash-образ | provenance фикстуры | — | **нет**: фикстуры синтетические |

Правило: **O4 без O3 — не оракул**, O3 без O5 — доказательство на синтетике, O1/O2 — вспомогательные. Пункт C6 закрывается только цепочкой **O5 → O3 → O4 = pass**.

### 13.3. Обязательные утверждения оракула (N1–N8)

| ID | Утверждение | Эталон | Состояние |
|---|---|---|---|
| **N1** | Поиск имени регистронезависим: создав `OSCAR`, том обязан открыть `oscar` | «Do not assume case sensitivity… NTFS supports POSIX semantics for case sensitivity but this is not the default behavior» — [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file); в `ntfs3` за это отвечает опция `nocase` — [docs.kernel.org](https://docs.kernel.org/filesystems/ntfs3.html) | **нет**: сравнение через `$UpCase` в `mountfile/ntfs_*.py` отсутствует (grep по `casefold|upcase|nocase` пуст); `$UpCase` валидируется только внутри `$ATTRIBUTE_LIST` (`ntfs_reader.py:525`) |
| **N2** | Именованные потоки: `file:stream:$DATA`, дефолтный поток — `sample.txt::$DATA` | [MS-FSCC](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/c54dec26-1551-4d3a-a0ea-4fa40f848eb3): «The default data stream has no name… `sample.txt::$DATA`»; в `ntfs3` — опция `ads` (включена по умолчанию) и псевдо-поток `query_streams` | **нет**: обработки ADS в `mountfile/ntfs_*.py` не найдено |
| **N3** | Индексный поток каталога — `$I30:$INDEX_ALLOCATION` | тот же MS-FSCC: «Directories are the stream type `$INDEX_ALLOCATION`… default stream name… `$I30`» | **нет** — прямая связь с C3 (индексная хирургия) |
| **N4** | Запрещённые имена и хвостовые точка/пробел отвергаются на записи | зарезервированные символы `< > : " / \\ | ? *`, `0x00`, `0x01–0x1F`; имена `CON, PRN, AUX, NUL, COM1-9, LPT1-9` (и с расширением); «because the last character is a space or a dot» — [naming-a-file](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file), `windows_names` в `ntfs3` | **не подтверждено**: `validate_internal_path` (`mountfile/native_write.py`) есть, но его содержимое я не читал |
| **N5** | `$ATTRIBUTE_LIST` с cross-record целью — типизированный отказ, не тихий пропуск | `mountfile/ntfs_logfile.py:1802` («`$LogFile` record uses `$ATTRIBUTE_LIST`; cross-record attribute…»), `mountfile/ntfs_replay.py:1168` | **есть** (C4 — осознанный отказ) |
| **N6** | Crash-образ грязный до ремонта и чистый после; `ntfsfix -d` снимает dirty только «if the volume can be fixed and mounted» | [ntfsfix(8)](https://manpages.debian.org/bookworm/ntfs-3g/ntfsfix.8.en.html) | есть частично: `mark_volume_dirty` в фикстуре, dirty-флаг проверяется в oracle-matrix |
| **N7** | Коды возврата `chkdsk` интерпретируются правильно: `0` — ошибок нет; `1` — ошибки найдены и исправлены; `2` — cleanup или не исправлялось без `/f`; `3` — проверить не удалось | дословная таблица — [chkdsk](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/chkdsk) | **риск**: для грязного crash-образа `1` — это **ожидаемый успех**, а `2`/`3` — `blocked`/`unavailable`, не `pass` |
| **N8** | Монтирование dirty-тома само способно делать replay | `ntfs3`: «Supports native journal replaying»; todo: «Full journaling support over JBD. Currently journal replaying is supported which is not necessarily as effective as JBD would be» — [docs.kernel.org](https://docs.kernel.org/filesystems/ntfs3.html) | требование к оракулу: только копия, приоритет `ro`; `force` — только на копии, «Not recommended for use» |

N7 — самая практичная находка: харнесс, который считает любой ненулевой код `chkdsk` провалом, будет вечно красным на корректном ремонте, а харнесс, который считает `2` успехом, — вечно зелёным на «не проверяли».

### 13.4. Маппинг на пункты манифеста

| Пункт | Закрывается | Чем именно |
|---|---|---|
| **C6** ⚠️ | O5 → O3 → O4 | захваченный crash + `chkdsk` + 4 потока = `pass` |
| **D5** ⚠️ | O2 + O3 | «авторитетный чекер» = независимый парсер ядра и/или `chkdsk`, а не `ntfsfix` |
| **C3** ⚠️ | N3 + O4 | индексный поток `$I30` в сравнении, а не только `$BITMAP` |
| **C4** 🚫 | N5 | остаётся отказом по проекту, оракул лишь фиксирует типизированность |
| **B8/D2** ⚠️ | O5 | provenance фикстуры и kill по фазам на ней |

Правка `checker-matrix.json`: добавить строку
`{"profile": "ntfs-native-rw", "checker": "chkdsk", "checker_authoritative": true, "checker_package": "windows", "availability": "…", "parity": "not_claimed"}`
и переводить `parity` в `pass` **только** при O4 = `pass` на O5-фикстуре. Сейчас такой строки нет ни в одном состоянии.

### 13.5. Предлагаемый артефакт `mountfile.ntfs-oracle/v1`

`docs/generated/ntfs-oracle.json` + генератор `scripts/ntfs_oracle.py`:

```json
{
  "schema": "mountfile.ntfs-oracle/v1",
  "slice": {"commit": "…", "version": "…", "checked": "YYYY-MM-DD"},
  "fixtures": [{"id": "…", "provenance": "synthetic|windows_capture", "sha256": "…"}],
  "tiers": [{"id": "O3", "tool": "chkdsk", "authority": "windows_native",
             "availability": "available|unavailable", "result": "pass|fail|blocked|unavailable"}],
  "assertions": [{"id": "N1", "kind": "case_insensitive_lookup",
                  "verdict": "pass|fail|blocked|unavailable", "evidence": ["…"]}],
  "summary": {"pass": 0, "fail": 0, "blocked": 0, "unavailable": 0,
              "not_claimed": ["parity_with_windows_chkdsk"]}
}
```

Коды выхода `scripts/ntfs_oracle.py --check`: `0` — все утверждения `pass`; `1` — есть `fail`; `2` — есть `blocked` (типизированный отказ replay); `3` — авторитетный ярус `unavailable`, а `parity: pass` заявлен (противоречие, которое сейчас нечем поймать).

Инварианты, как в `replay-acceptance.json`: `pass` без `evidence` запрещён; `unavailable` не может стоять рядом с `parity: pass`; `windows_capture` обязан нести `sha256` и `github_run_id`.

### 13.6. Acceptance-тесты

- `tests/test_ntfs_oracle_contract.py` — схема, инварианты, отсутствие `pass` без доказательств.
- `tests/test_ntfs_oracle_matrix.py` — прогон N1–N4 на реальном `mkntfs`-томе через O2 (skip, если `ntfs-3g`/`ntfs3` недоступны), N7 — юнит-тест маппинга кодов `chkdsk`.
- Windows-лег: O3 → O4 → артефакт `ntfs-oracle.json` в upload; гейт `--check` в CI.

### 13.7. Чего этот оракул не доказывает

- Microsoft **не называет** `chkdsk` «authoritative» — это проектная модель (`checker_authority = "windows_native"` в PS1), а не заявление вендора. Формулировать надо как «чекер Windows как эталон проекта», иначе claim сильнее источника.
- O1 и O2 не заменяют O3: `ntfsfix` по man page «NOT a Linux version of chkdsk», `ntfs3` journal replay «not necessarily as effective as JBD».
- O5 отсутствует: все текущие фикстуры синтетические, поэтому даже полный O3+O4 = pass останется доказательством на синтетике, пока не появится Windows-захват.
- Не подтверждено: содержимое `validate_internal_path`; поддержка ADS/`$I30`/`nocase` в runtime-ридере; поведение `ntfs3` при монтировании dirty-тома без `force`; фактические коды возврата `chkdsk` на конкретном VHDX-фикстуре (в этом прогоне Windows-раннера не было).
