# Native exFAT multi-FAT profile

The bounded native exFAT provider uses the validated boot-region `NumberOfFats` and `VolumeFlags` metadata. Bit 0 (`ActiveFat`) selects the active FAT and allocation bitmap; the selected copy is used for chain traversal and allocation checks. The boot and backup regions must agree on geometry, including `NumberOfFats`; status fields such as `VolumeFlags` and `PercentInUse` may be stale in the backup copy.

The field definitions follow the [Microsoft exFAT File System Specification](https://learn.microsoft.com/en-us/windows/win32/fileio/exfat-specification), Table 5: bit 1 is `VolumeDirty`, bit 2 is `MediaFailure`, and bit 3 is `ClearToZero`. The reader remains read-only and never repairs or clears these flags. The writer refuses a dirty volume, a volume reporting media failure, or a set `ClearToZero` flag because this profile does not implement the required pre-write flag transition. Bits 4–15 are reserved and rejected by the boot-region probe. A two-FAT write mirrors ordinary FAT updates to both declared copies, while the selected active copy remains authoritative for reads. Existing one-FAT images retain their previous behavior.

File streams honor the exFAT `NoFatChain` flag. Contiguous streams are read directly from the cluster heap without interpreting FAT entries; ordinary streams are bounded by the cluster count and reject cycles, invalid links, overlong chains, and cross-linked ownership. The allocation bitmap is authoritative for stream allocation, while ordinary free-cluster allocation also requires a zero active-FAT entry. Entry-set checksums, filename hashes, Unicode up-case collisions, `ValidDataLength`/`DataLength`, and directory stream lengths are validated before mutation.

Writes are staged in a same-directory temporary image, read back through the native reader, and published only after source identity and selected-volume bounds are rechecked. Unsupported metadata layouts and inconsistent mandatory system entries refuse before the source image is changed.
