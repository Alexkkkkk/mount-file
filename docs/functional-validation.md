# Что исправлено и как проверить

В ветке `fix/full-functional-audit-2026-11-05` проведена сквозная проверка пользовательских сценариев MountFile. Исправления и результаты опубликованы в [pull request #373](https://github.com/Alexkkkkk/mount-file/pull/373). Исходный `main` включён в ветку.

Проверка не означает, что каждая файловая система поддерживает полный объём её спецификации. MountFile продолжает отказывать на неизвестных, испорченных, dirty и неподдерживаемых профилях. Успешная проверка одного примера не превращает экспериментальный или legacy writer в универсальный.

## Основные изменения

Исправлены реальные GUI-пути открытия и смены дискового образа, обеих панелей, вкладок, копирования файлов и каталогов, редактирования текста и HEX, повторного сохранения, безопасного извлечения, резервирования и остановки приложения. Добавлены offscreen-регрессии.

Исправлены ограниченные FAT12/16/32 операции и проверки геометрии, exFAT чтение/запись, отдельные поля NTFS MFT и индексов, ext4 timestamp parsing, границы выбранного тома, путь автоматического выбора раздела, CLI backups, fail-closed маршрутизация и извлечение. В `WriteEngine` профиль операции сохраняется при закрытии фасада перед checker; необоснованное чтение закрытого фасада приводило к отказу каждой транзакции. Опасная незавершённая переименовывающая операция debugfs заменена на проверяемое связывание и удаление обычных файлов; неподдерживаемые операции должны отказываться явно.

Исправлены упаковка wheel, включение ресурсов, установка дополнительных профилей, Linux/macOS/Windows installer scripts, standalone-helper, обновления, REST/AI/MCP и несколько путей OLMA/DFIR. Установленные команды `mountfile-rw` и `mountfile-rw-v2` теперь принимают системный `argv` без обязательного аргумента. Общий smoke-launcher возвращает ошибку, если завершилась с ошибкой дочерняя проверка. Добавлена сверка описания установки и smoke-инструкций.

Для полного запуска после установки dev-зависимостей используйте:

```bash
QT_QPA_PLATFORM=offscreen PYTHONPATH=. python -m pytest -q
python -m ruff check . --select E9,F63,F7,F82,B006,E722,S110,S112,F841
python -m black --check .
python -m isort --check-only .
git diff --check
```

Если checker-тесты пропускаются, установите `dosfstools`, `mtools`, `exfatprogs`, `ntfs-3g`, `e2fsprogs`, а затем повторите.

## Второй круг: CLI на реальных образах и кроссплатформенные тесты

После публикации ветки оставались десять падений Windows-матрицы и несколько
дефектов, которые не ловятся юнит-тестами: они проявляются только на настоящем
образе, созданном `mkfs`, и только при вызове реальной команды.

Исправлено в коде:

- **`yara --rules`**. Путь к файлу правил передавался как YARA-исходник, поэтому
  каждая команда завершалась `syntax error`. Теперь компилируется файл, а
  `mountfile/dfir_yara.py` не принимает `pathlib.Path` за скомпилированные
  правила (у `Path` есть собственный `match()`).
- **`yara-scan` по образу**. Скан прерывался на первой нечитаемой записи: метка
  тома FAT отдаётся файловым API как обычный файл, а `File_read_random`
  возвращает ошибку. Такие записи пропускаются с предупреждением в журнале,
  пустые файлы не читаются.
- **`yara-scan` по unallocated**. Путь образа записывался атрибутом в
  pytsk3-объект, который атрибуты не принимает, и скан падал с
  `image source is unavailable`. Путь передаётся явным аргументом.
- **Extent тома в GUI**. Граница тома вычислялась по всем найденным сигнатурам,
  включая заголовки файловых систем внутри тома. Образ NTFS/exFAT целиком
  (без таблицы разделов) из-за этого открывался только для чтения с отказом
  `declared size exceeds the selected volume bounds`. Границы берутся из таблицы
  разделов, для образа без таблицы extent равен размеру файла.
- **HEX-редактор**. `HexEditorPage.save()` молча ничего не делал при отказе;
  теперь он возвращает результат и показывает причину отказа.
- **Standalone `LinuxBackend`**. На платформе без `os.geteuid` монтирование
  падало `AttributeError` вместо понятного `MountError`.

Тесты стали переносимыми: Linux-only loop/udisksctl сценарии пропускаются там,
где нет `os.geteuid`; `.cmd`-скрипт обновления читается как UTF-8 (а не в
ANSI-кодировке Windows); выбор релизной сборки в тестах автообновления не
зависит от архитектуры раннера; offline-сборка wheel пропускается с явной
причиной, если в окружении нет `setuptools`.

Сквозная проверка вынесена в репозиторий:

```bash
scripts/smoke-real-images.sh /tmp/mountfile-smoke
# or, equivalently:
make smoke-images WORK=/tmp/mountfile-smoke
```

Скрипт сам создаёт образы (`mkfs.vfat`, `mkfs.exfat`, `mkfs.ext2`, `mkfs.ext4`,
`mkfs.ntfs`) и проверяет каждую операцию внешним инструментом, а не тем же
писателем: `mtools` и `fsck.vfat` для FAT32, `fsck.exfat` для exFAT, `e2fsck`
для ext2. Он покрывает чтение, извлечение, запись, `mkdir`/`mv`/`rm`, отказ без
`--yes`, DFIR-команды (`hash`, `grep`, `search`, `timeline-build`,
`timeline-query`, `timestomp-scan`, `yara`, `yara-scan`, `unallocated-scan`,
`slack-extract`, `evidence-manifest`, `live-diff`), декодирование и разбиение
дампов RT809H и offscreen-запуск GUI с проверкой, что том открылся на запись.

Результат на этом коммите: полный набор **2351 passed, 2 skipped, 0 failed**
(пропуски — отсутствующие `PIL` и PowerShell в Linux-окружении), сквозной smoke
**70 passed, 0 failed, 0 skipped**, `ruff` correctness-гейты, `black --check` и
`isort --check-only` чистые, проверка согласованности версий
`python tools/mfsync.py check --strict` проходит.

## Оставшиеся ограничения

Native NTFS и native ext3/ext4 writing не включались; native NTFS metadata listing и чтение поддерживаемых потоков проверены, а неподдерживаемый `$BadClus:$Bad` явно остаётся нечитаемым. Поддержка ограничена конкретными allowlisted профилями файловых систем. Успешность real-image checker и полного автоматического набора не доказывает полную матрицу всех профилей, операций и состояний.

OS-level privileged mounts и Windows ImDisk пути проверялись ограниченно либо в mocks. Legacy `RebuildRW` и cleanup paths ограничены staging, проверками и fail-closed rollback; по-прежнему требуется проверять их на целевых ОС и сценариях восстановления. Установка контейнера на Docker Engine и сборка Windows/macOS бинарников в данной Linux-среде не подтверждены.

Нельзя считать выполненным полное завершение #182: остаются различные acceptance gates, полная независимая матрица writer × operation, crash/power-loss matrix и кроссплатформенные проверки.
