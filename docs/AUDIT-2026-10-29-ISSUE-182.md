# MountFile / issue #182 — аудит синхронизации

**Снимок:** 2026-10-29. **`main` baseline:** `c63e10f` (`v1.58.2`). Текущие изменения разрабатываются в draft [PR #220](https://github.com/Alexkkkkk/mount-file/pull/220); live head/checks смотреть там же. Draft изменения не входят в `main` до merge.

## Вывод

Roadmap issue #182 существенно реализован: native VFS работает offline-by-default, поддерживает bounded read-only profiles FAT12/16/32, ext2/3/4, NTFS и exFAT, а native writes существуют для ограниченных профилей FAT32, ext2 и exFAT. Это не полное соответствие спецификациям файловых систем, не универсальная crash-safety и не закрытие всей acceptance matrix.

В `main` уже есть provider capabilities/status, fail-closed routing и защита extraction. Draft PR #220 добавляет schema-v1 machine-readable operation matrix в `mountfile.capabilities` для 8 bounded read profiles и 3 native writer profiles; `vfs_api` и native RW strategy status используют её vocabularies. Native writer operations публикуются только при writable flag и точном совпадении filesystem/backend/strategy с профилем. Это полезный источник согласованных API operations, но не полный `format × profile × image-state × operation` validator matrix и пока не часть `main`. Общий `checked_range` helper и central typed refusal type вроде `RefusalError` по-прежнему отсутствуют.

## Матрица возможностей в `main`

| Профиль | Native read | Native write | Ограничения, которые должны оставаться видимыми |
|---|---|---|---|
| FAT12/16 | bounded list/stat/read/range/extract | нет | mutation явно отвергается; системный ImDisk — отдельный Windows compatibility route |
| FAT32 | bounded list/stat/read/range/extract | put/replace, mkdir, rename, delete в ограниченном native профиле | геометрия и selected extent проверяются; rollback/staging не обещают power-loss atomicity |
| ext2 | bounded list/stat/read/range/extract | clean allowlisted profile: put/replace, mkdir, rename, delete file/empty directory | блоки 1/2/4 KiB; writer direct + single-indirect, до `12 + block_size/4` блоков на объект; sparse и double/triple-indirect writes не поддерживаются |
| ext3 | bounded read-only; поддержанный clean профиль и ограниченная JBD2 validation | нет | opt-in in-memory replay только ограниченного линейного descriptor/data/commit формата; не полноценное recovery и не writer |
| ext4 | bounded read-only classic/extent profile | нет | 64-bit, flex_bg, bigalloc, metadata_csum и ряд layout/features отвергаются; CRC32C helper не означает проверку всех metadata checksums |
| NTFS | bounded read-only metadata/tree profile: list/stat/read-range/extract | нет | явный extent, проверки boot/MFT/USA/index/volume state/clean `$LogFile` restart metadata; max 1 MiB на range read; нет journal replay, `ATTRIBUTE_LIST`, sparse/compressed/encrypted streams и native writes |
| exFAT | bounded list/stat/read/range/extract | ограниченный put/replace, mkdir, move/rename, delete | один FAT, нулевые `VolumeFlags`, проверенные boot/system metadata; unsupported профили отвергаются |

Reader и writer capability различаются. Возможность вызвать CLI-команду `put`, `mkdir`, `mv` или `rm` сама по себе не означает, что выбранный backend разрешает операцию на конкретном image.

## Общие routing и safety свойства

- `mountfile/vfs.py` выбирает один native профиль. `pytsk3`/`libtsk` остаётся optional и explicit opt-in для compatibility; распознанный, но malformed/dirty/unsupported filesystem не должен молча переходить на другой parser.
- `mountfile/capabilities.py` в PR #220 содержит serializable matrix и общие operation vocabularies; `mountfile/vfs_api.py` и native `UniversalFSRW.backend_status` используют эти constants. Registry сверяется тестами, но не заменяет profile validation и ещё не задаёт ограничения/состояния каждого parser-а.
- Readers и writers проверяют bounds в форматных реализациях. Единого публичного `checked_range` нет; его нужно вводить постепенно и интегрировать во все call sites, а не считать уже реализованным.
- Extraction ограничивает destination безопасным каталогом и предотвращает traversal/symlink escapes. В PR #220 дополнительно ограничивается размер read-range по provider `max_read_range_bytes`.
- Native writer staging, hash/re-check, locking, read-back, rollback и quarantine — отдельные профильно-специфичные защиты. Они не доказывают атомарную долговечность при сбое ОС/накопителя или отключении питания.
- Ошибки уже содержат сообщения и некоторые профильные типы, однако единого typed refusal taxonomy/code API (`RefusalError` и категории unsupported/dirty/corrupt/out-of-bounds/unsafe) нет.

### Профильные подробности и тестовые указатели

**FAT.** `mountfile/fat_reader.py` реализует bounded native read для FAT12/16/32; `mountfile/fat32.py` и `mountfile/universal_fs_rw.py` реализуют ограниченные FAT32 mutations. FAT12/16 native write отвергается. Тесты `tests/test_fat_reader.py`, `tests/test_fat32_write.py` и `tests/test_fat_rw_bounds.py` покрывают differential read, CRUD, границы extent, rollback и отказ небезопасных профилей.

**ext2.** Reader принимает bounded clean profiles, поддерживает indirect mapping и ограничивает один range request 16 MiB. Writer требует чистый allowlisted non-journaled профиль; принимает direct + single-indirect для содержимого и роста каталогов, но отвергает sparse и double/triple-indirect writes. Удаление каталога ограничено пустыми каталогами; hard links и некоторые inode metadata не имеют общей write parity. Подробности и отказные тесты: `mountfile/ext2_native.py`, `mountfile/ext2_reader.py`, `tests/test_ext2_native.py`, `tests/test_ext2_reader.py`, `tests/test_ext2_writer_lock.py`.

**ext3/ext4.** `NativeExt3Image` принимает только ограниченный профиль. Journal replay, когда явно запрошен, публикует проверенный in-memory overlay и не пишет в image; ring wraparound, revoke, journal checksums и полноценное checkpoint/recovery покрытие отсутствуют. ext4 поддерживает ограниченный classic/extent read; 64BIT, flex_bg, bigalloc, metadata_csum, indexed directories и другие layouts остаются reject. См. `mountfile/ext3_reader.py`, `mountfile/ext_checksum.py`, `tests/test_ext3_reader.py`, `tests/test_ext_checksum.py` и [план профилей](ext3-ext4-readonly-plan.md).

**NTFS.** Reader проверяет geometry, primary/backup boot sectors, MFT/MFTMirr, USA fixups, bounded attributes/runlists, индексы, `$Volume` и clean `$LogFile` restart metadata. Это не `$LogFile` replay и не полный NTFS parser; `ATTRIBUTE_LIST` и sparse/compressed/encrypted streams не поддерживаются. Read-range ограничен 1 MiB. См. `mountfile/ntfs_reader.py`, `mountfile/ntfs_mft.py`, `mountfile/ntfs_probe.py` и `tests/test_ntfs_*.py`.

**exFAT.** Bounded reader/writer используют проверенные boot/system metadata и выбранный single-FAT profile с нулевыми volume flags. Writer поддерживает проверенные file/directory operations, но не произвольный exFAT layout и не on-volume recovery. См. `mountfile/exfat_reader.py`, `mountfile/exfat_probe.py`, `mountfile/exfat_writer.py`, `tests/test_exfat_probe.py`.

## Что изменяет draft PR #220

На проверенном diff относительно `main`:

- ext2 reader кэширует directory listings; ext3/ext4 reader coalesces/caches bounded extent reads. Это оптимизации, а не новые filesystem features или writers;
- NTFS/exFAT reader выставляют публичную характеристику уже ограниченного read-range;
- exFAT writer добавляет защиту host target identity: отказы для symlink/reparse point, hardlink и смены объекта между проверкой/open; добавлены focused tests;
- extraction применяет provider `max_read_range_bytes` как ceiling на chunks;
- README, landing page, audit/plan text и benchmark artifact уточняются, чтобы различать main, draft и будущие работы.

PR #220 — открытый draft. На SHA `eed058d` при проверке было 17 successful, 6 skipped, 3 pending и 0 failing. Это лишь снимок checks на том SHA; при новых commits нужен новый CI run. Live status: https://github.com/Alexkkkkk/mount-file/pull/220.

## Acceptance и benchmarks

1. **Native read без обязательного `pytsk3`: частично/по accepted bounded profiles.** Все перечисленные форматы имеют ограниченные reader profiles, но это не полный parity всех layouts и повреждённых/экзотических образов.
2. **Native write без скрытых CLI: частично.** Только bounded FAT32/ext2/exFAT operations; native ext3/ext4/NTFS writers отсутствуют.
3. **Cross-platform regression matrix: частично.** CI workflow задаёт Linux/macOS/Windows jobs, но конфигурация workflow сама по себе не доказывает успешный прогон каждого commit. У sandbox есть только Linux local run.
4. **Read-back/independent checks/failure injection: частично.** Есть тесты на конкретных writer profiles и failure points; нет полного fault/crash/power-loss доказательства для всей операции matrix.
5. **GUI/CLI/VFS/status/docs: частично.** Draft PR #220 вводит serializable operation matrix и использует общий vocab для VFS и native RW status; нужны state/feature limits для каждого профиля и полная сверка GUI/CLI с registry.
6. **Benchmark target: достигнут на опубликованном измеренном ext2 workload, но не обобщён.** В `docs/benchmarks.md` два content-equivalent прогона на Linux ARM64 показывают native быстрее `pytsk3` на 1 MiB range-read и 10 MiB extraction. Это удовлетворяет порогу ≤20% slower именно для указанной fixture/environment, не для всех FS/OS/storage. Draft `benchmarks/results/README.md` добавляет synthetic ext2 matrices и allowlisted ext4 workload (в одном ext4 профиле reported 3.8% regression), также не универсальный performance claim.

## Оставшиеся приоритеты

**P0:** расширить operation matrix из PR #220 до проверяемых profile/state/feature limits и подключить к GUI/CLI reporting; внедрить и постепенно подключать единый `checked_range` с image и partition bounds; ввести typed refusal codes.

**P1:** продолжать property/fuzz tests для runlists, extent trees, cluster chains, records, sizes и cycles; расширить cross-platform locking/rollback/failure injection; добавить representative real-image corpus и дифференциальные сверки. Не заявлять power-loss guarantees без специального доказательства.

**Отдельные будущие работы:** native ext3/ext4 writer с journal ordering/checksums/recovery; NTFS `$LogFile`-aware transactional writer; расширение exFAT layout support; optional FUSE/WinFsp/macFUSE adapter. Каждый такой этап требует отдельного профиля, независимой проверки и отказных тестов.

## Итог

Issue #182 существенно реализован, но roadmap остаётся открыт. В `main` уже есть bounded native reads всех перечисленных семейств и ограниченные FAT32/ext2/exFAT writers. PR #220 дополнительно содержит hardening/оптимизации, docs synchronization и initial machine-readable operation matrix; до merge она не является частью `main`, а typed refusal codes и единый checked-range контракт остаются будущей работой. Не заявлять полную filesystem parity, универсальное journal recovery или гарантированную сохранность при любом power loss.
